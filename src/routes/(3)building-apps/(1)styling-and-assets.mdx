Solid has no styling opinion of its own.
Styles and assets enter through Vite's import pipeline, the same as in any Vite project, and a component decides how to apply them with the `class` and `style` props.
What is different in a start-mode project is that there is no `index.html` to put a `<link>` in, so everything reaches the page through imports.

This page walks the choices in the order most projects meet them.

## Pick a styling approach

**Global CSS** is the default in every template.
Import a stylesheet for its side effect and its rules apply everywhere:

```tsx
// src/App.tsx
import "./App.css";
```

Where you import it does not scope it; a stylesheet imported from one route module still applies to every page once that module has loaded.
Treat this as the place for resets, typography, and layout.

**CSS modules** give a component classes that cannot collide.
Name the file `*.module.css` and import the class map:

```tsx
import styles from "./Card.module.css";

export function Card(props: { title: string }) {
	return <article class={styles.card}>{props.title}</article>;
}
```

```css
/* Card.module.css */
.card {
	border-radius: 0.5rem;
	padding: 1rem;
}
```

`styles.card` is a generated class name, so two components can each have a `.card` rule.
This is the right default for component-level styles.

**Tailwind** works through its Vite plugin, with no Solid-specific setup.
The `with-tailwindcss` template adds the plugin and one import:

```ts
// vite.config.ts
import tailwindcss from "@tailwindcss/vite";

export default defineConfig({
	plugins: [solid({ start: true }), fileRoutes(), tailwindcss()],
});
```

```css
/* src/App.css */
@import "tailwindcss";
```

**Sass and other preprocessors** need only the compiler installed.
The `with-sass` template renames `App.css` to `App.scss` and changes the import to match; `*.module.scss` combines both.
The preprocessor runs at build time and ships nothing to the browser.

## Conditional classes and inline styles

Whichever approach supplies the class names, Solid's `class` prop accepts an object or an array so a component can toggle them without string building:

```tsx
<li class={{ [styles.row]: true, [styles.selected]: props.selected }}>…</li>

<button class={["btn", { "btn-primary": props.primary }]}>…</button>
```

A string is always applied, an object adds each key whose value is truthy, and an array combines the two.
Put conditions in the object rather than building a string; Solid then adds and removes only the affected class tokens.

`style` takes an object of CSS declarations and updates only the declarations that change:

```tsx
<div style={{ width: `${progress()}%`, "background-color": color() }} />
```

Both are read reactively when given a function or a tracked value.
The [`class`](/reference/solid-web/jsx-properties/class) and [`style`](/reference/solid-web/jsx-properties/style) reference pages have the details, including how object forms interact with stores.

## Images and other files

Import a file when code needs its URL.
Vite hashes it into the build output and the import gives you the final path:

```tsx
import logo from "../logo.svg";

<img src={logo} alt="Solid logo" />;
```

The templates set `build.assetsInlineLimit: 0` so small images stay as files rather than being inlined as data URLs into the JavaScript.
Remove that if you prefer inlining for icons.

Append `?url` to import something as a URL that Vite would otherwise process, such as a stylesheet you want to link rather than inject:

```tsx
import themeHref from "./theme.css?url";

<link rel="stylesheet" href={themeHref} />;
```

Files that need a fixed, un-hashed path go in `public/` and are referenced by root-relative URL.
The `basic` template keeps `favicon.ico` there and fetches `public/users.json` as `/users.json`:

```tsx
<link rel="icon" href="/favicon.ico" />
```

Use `public/` for things an outside party needs to find by name: `robots.txt`, a well-known file, an image referenced from an email.
Import everything else, so a changed file gets a new URL and caches cannot serve the old one.

A stylesheet imported by a lazy route module is loaded with that module's chunk.
For a page that must be styled before its JavaScript arrives, import its CSS from a module that is always loaded, or add a `<link>` for it through [head metadata](/building-apps/head-and-metadata).

:::deep-dive[Why there is no flash of unstyled content]
In production, the CSS reachable from `App` and `Document` is built into asset files and the generated handler writes `<link rel="stylesheet">` tags for them into the document head, so the first HTML the browser receives already references the styles.
Imported asset URLs point at their hashed output.

In development, the dev server inlines the reachable CSS into the server-rendered page so the first paint is styled, then Vite's client takes over for hot updates and the server-rendered copy is removed.
You may briefly see two `<style>` elements for the same file in the inspector during that handoff; it is expected.
:::

## Common problems

**A CSS module class is `undefined`.**
The file is not named `*.module.css`, or the class in the CSS uses a name that is not a valid identifier; `styles["my-class"]` works, `styles.my-class` does not.

**Styles from one page leak into another.**
The stylesheet is global CSS imported from a route module.
Switch to a CSS module or scope the selectors under a page-level class.

**An imported image has a `data:` URL.**
It was small enough to inline.
Set `build.assetsInlineLimit: 0` or move it to `public/`.

**A `public/` file 404s in production.**
The host is not serving `dist/client` for that path.
[Deployment](/building-apps/deployment) shows how each host maps static files.
