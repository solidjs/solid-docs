A `<Loading>` boundary needed 3+/4+ render passes — 2+/3+ sequential async waits (dev).

## What you saw

- **Kind:** `ssr`
- **Severity:** `info` (advisory, delivered on the diagnostics channel and never printed) or `warn` (code that works but is structurally wrong or expensive)

The console report opens with `[SSR_BOUNDARY_WATERFALL]` and the message, then an `in` line naming the owners that enclose the subject, root first, and an `at` line with the source location when the code was compiled with one.
In a captured artifact the same finding is an event with `code: "SSR_BOUNDARY_WATERFALL"`, `ownerPath`, and `loc`.
[Diagnostics](/reference/solid-js/diagnostics#read-a-report) explains each line.

## Why it fires

A `<Loading>` boundary rendered in `data.passes` passes — discovery, then one per wait — and each pass past the first is a read that could only start once the previous pass's async answered: `passes - 1` sequential waits, `data.sequentialMs` end to end.
Unlike the client's [`ASYNC_WATERFALL`](/reference/solid-js/diagnostics/async-waterfall) this proof is exact (the pass structure IS the chain), so there is no `markFlight` false positive to rule out.

:::note[Server rendering]
The server runtime reports on the same channel, with the same `in <App> › <Page>` line.
Two groups.
**Findings** ([`SSR_RENDER_ERROR_CONTAINED`](/reference/solid-js/diagnostics/ssr-render-error-contained), [`SSR_SUBTREE_ABANDONED`](/reference/solid-js/diagnostics/ssr-subtree-abandoned), [`SSR_STREAM_ABANDONED`](/reference/solid-js/diagnostics/ssr-stream-abandoned), [`LATE_HEADER_WRITE`](/reference/solid-js/diagnostics/late-header-write), [`DYNAMIC_ASYNC_COMPONENT`](/reference/solid-js/diagnostics/dynamic-async-component), [`SERVER_ERROR_SANITIZED`](/reference/solid-js/diagnostics/server-error-sanitized), [`FRAME_MARKER_CORRUPTED`](/reference/solid-js/diagnostics/frame-marker-corrupted)) are facts about a render that exist in observe builds too — an APM sees them in production; in dev they print.
**Checks** (the rest, `SSR_BOUNDARY_WATERFALL` and [`SSR_CLIENT_CONTENT_MASKED`](/reference/solid-js/diagnostics/ssr-client-content-masked) included) are dev-only guidance.
A captured artifact from a server render carries both.
:::

## How to fix it

The same repairs apply, in the same order: derive both reads from the same inputs so they start together (read ALL async sources before using any), or, if the dependency is intrinsic, preload the dependent data or join the requests.
Two waits are `info` — a lead; three or more `warn`.
The boundary is `data.boundary`; a captured artifact has its record in `artifact.records.boundary` (same `id`) and the server-function calls under it in `artifact.records.invocation` (`boundary` field).
