The same router instance renders on the client and server.
No separate server router is required.

## Select the server URL

When a request event is available, the router reads `event.request.url`.
For static generation, tests, or another render without a request event, pass a `url` prop:

```tsx
const html = await renderToStream(() => (
	<Router url="https://example.com/users/42" />
));
```

A request event takes precedence over the `url` prop.
Only the pathname and search string select the server route.
Client history adapters do not select the location for a server render, although their utility overrides remain available.

## Stream lazy route subtrees

A matched lazy `children` thunk is asynchronous route work.
The router waits for the subtree, recompiles the route branches, and then renders its inner match.

Use the streaming server-rendering entry for a route tree that can cross a lazy subtree:

```tsx
import { renderToStream } from "@solidjs/web";

const html = await renderToStream(() => <Router url={request.url} />);
```

Awaiting `renderToStream` returns the settled HTML in the source revision documented here.
The synchronous `renderToString` path does not support a matched lazy route subtree.

## Hydrate query results

During an asynchronous server render, `query` serializes its keyed result into Solid's hydration registry unless the render disables hydration or the request is marked server-only.
The client query with the same name and serialized arguments adopts that server result instead of starting a duplicate request.

The adoption path remains available after global hydration completes because a lazy route module can make its first matching query read later.
At this source revision, the server payload must be younger than the query cache retention limit of three minutes.
A first read after that limit runs the query again instead of presenting the old server value as newly fetched.

Keep the query name and arguments stable between server and client.
The cache key is the query name followed by the serialized argument array.

## Collect fresh data with mutations

The optional `@solidjs/router/server` entry connects route preloads to Solid's server-function single-flight protocol.
Create the collector from the same router instance:

```ts
// src/server-config.ts
import { createFlightDataCollector } from "@solidjs/router/server";
import { configureServerFunctionsServer } from "@solidjs/web/server-functions/server";
import { Router } from "./router";

configureServerFunctionsServer({
	collectFlightData: createFlightDataCollector(Router),
});
```

The collector receives the mutation outcome from the server-function handler.
It matches the URL the client will show after the mutation, resolves any matching lazy route subtrees, runs the root preload, and runs the matched route preloads in data-only mode.
`query` calls made by those preloads become keyed values in the mutation response.

On the client, a mounted router subscribes to flight data when `singleFlight` is enabled.
That subscription opts server-function mutations into the protocol.
Delivered values seed the query cache, then response revalidation and redirect metadata are applied before the action caller receives its return value.

Set `singleFlight: false` to keep the router from subscribing.
Without a consumer, the transport does not add the single-flight request header and the server does not run collection for that mutation.

## Register the collector before dispatch

When `vite-plugin-solid` compiles server functions, its `serverFunctions.configure` option can pin a server-only configuration module into the generated handler graph:

```ts
// vite.config.ts
import solid from "vite-plugin-solid";

export default {
	plugins: [
		solid({
			serverFunctions: {
				configure: "./src/server-config.ts",
			},
		}),
	],
};
```

The generated handler imports that module before it configures and dispatches server-function requests.
This keeps the collector registration available for the first mutation in development and production.
The default server-function endpoint is `/_server`; keep the router's `actionBase` aligned with a customized endpoint.

Applications with a custom server-function handler can instead pass `collectFlightData` to `handleServerFunctionRequest` for each request.

## Preserve form behavior without JavaScript

An action backed by a server function has a URL that a POST form can submit without the client runtime.
The Solid server-function runtime handles that no-JavaScript post by redirecting back with the outcome in a one-shot flash cookie.
During the redirected server render, the router clears and decodes that cookie into submission state.

The router also intercepts server-action form URLs in clients where the action module was not loaded.
It loads the action submit path on demand and sends the form through the server-function transport.

This form path depends on the Solid server-function handler and its no-JavaScript handling.
Plain client-only actions cannot run without their client module.

See [`createFlightDataCollector`](/reference/solid-router/server#createflightdatacollector) for the collector options.
