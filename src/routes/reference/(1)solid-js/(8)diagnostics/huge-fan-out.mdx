## Why it fires

One value has very many subscribers, so a single change re-runs all of them (`data.count`).
Always on from 2000; while attribution is enabled the same code fires from `fanOut` (default 250) on a stamped root write, and `data.write` says which — a `write`, a `refresh`, or an `async` landing.
Classic signature: every row of a list comparing against one selected id.

:::note[Performance pathologies (from the attribution engine)]
These fire only while attribution is enabled and describe cost, not incorrect behavior.
The numbers in the message are measurements, not guesses.
:::

## How to fix it

Invert the question: keep the answer in a store used as a map keyed by id (`selected[row.id]` instead of `row.id === selectedId()`), so each consumer reads its own key and only the keys that flipped update.
When that map is derived from other state, `createProjection` builds it.
