## Why it fires

A `Loading` fallback appeared and vanished inside 150ms (`data.shownMs`): the data was nearly there, and the spinner read as a flicker.
This is the other end of [`SILENT_HOLD`](/reference/solid-js/diagnostics/silent-hold) — too much feedback for too little wait — and it is `info`, a count to read (`feedback().fallbacks[] .flashes` has the total per boundary).

:::note[Responsiveness (from the attribution engine)]
The runtime did the correct thing; the user saw nothing while it did.
These fire only while attribution is enabled.
:::

## How to fix it

Repairs:

- Preload or cache the data so it is present before the boundary asks (`markFlight` a preload started on hover or route match).
- Lift the read above the boundary when the parent already waits, so the child boundary never shows.
- For a boundary that has revealed once, let a later update hold instead of re-showing the fallback — that is the default; a flash on update means `on` is keyed to something that changes more often than the data.

Do NOT add a minimum-display timer to the fallback; that trades a flicker for a wait.
