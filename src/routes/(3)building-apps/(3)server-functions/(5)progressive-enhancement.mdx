A server function has an HTTP address, so a plain HTML form can post to it.
The server-function runtime detects that the request came from a form rather than the Solid client, decodes the body as one `FormData` argument, and handles the outcome in a way the browser can follow without JavaScript.

Application code normally reaches this through a router.
Solid Router's `action()` wraps the server function in a value that serializes to that address, so the same `<form action={...}>` works before hydration and is taken over by the router after it.
This page explains the transport underneath, for the parts of an app the router does not cover and for integrations that build their own form helpers.

## Post a form through a router action

Declare a server function that accepts one `FormData` argument, and wrap it with `action` from `@solidjs/router`:

```ts
import { redirect, respond } from "@solidjs/web";

export async function createTodo(form: FormData) {
	"use server";

	const title = String(form.get("title") ?? "").trim();
	if (!title) {
		throw respond({ error: "Enter a title" }, { status: 400 });
	}

	await database.todos.insert({ title });
	return redirect("/todos", { revalidate: "todos" });
}
```

```tsx
import { action } from "@solidjs/router";
import { createTodo } from "./todos";

const addTodo = action(createTodo);

<form method="post" action={addTodo}>
	<label>
		Title
		<input name="title" required />
	</label>
	<button type="submit">Add todo</button>
</form>;
```

The rendered HTML has an ordinary `action="..."` attribute pointing at the server function's URL, so the browser can submit the form with no client runtime.
The server detects an unscripted request by the absence of the `X-Server-Function-Instance` request header and decodes the form body as the single `FormData` argument.

The [Forms guide](/guides/forms) builds this out with validation, inline errors, and pending state.

## Submit a GET form

A GET form replaces the action URL's query string with the form fields.
When the query is not an encoded server-function argument list, the handler passes one `URLSearchParams` argument.

`GET()` returns a typed `ServerFunction` reference, so its `url` is available directly:

```ts
import { GET } from "@solidjs/web/server-functions";

export const search = GET(async (params: URLSearchParams) => {
	"use server";
	return database.search(String(params.get("q") ?? ""));
});
```

```tsx
<form method="get" action={search.url}>
	<input name="q" />
	<button type="submit">Search</button>
</form>
```

GET functions must remain safe and idempotent.
Do not use a GET form for a mutation.

## The reference URL

Every server-function reference carries `id` and `url` at runtime, on the client proxy and on the server-side callable alike.
The `url` is the address the function is invoked at, `<endpoint>/<id>`, and is what the router serializes into the form attribute.

Whether TypeScript knows about it depends on how the function was declared:

- References returned by `GET()` and `live()` are typed as `ServerFunction`, which declares `id` and `url`.
- A bare `"use server"` function keeps its declared function type.
  `url` is present at runtime but not in the type, so `createTodo.url` is a type error.

For form posts, use a router action rather than the URL.
An integration that must read the address from a bare declaration can narrow it to `ServerFunction` from `@solidjs/web/server-functions` after checking `isServerFunction(fn)`.

## Bind leading arguments

The function id lives in the URL path.
An integration can add JSON-safe bound arguments to the reserved `args` query parameter, while the submitted form remains the final `FormData` argument.
Solid Router's `action.with(...)` does this for application code.

Use `serverFunctionUrl(id, boundArgs)` when a router, form helper, or custom host must build this URL:

```ts
import { serverFunctionUrl } from "@solidjs/web/server-functions";

const address = serverFunctionUrl(updateTodo.id, [todo.id]);
```

Bound arguments must be JSON-safe.
The no-JavaScript form convention does not load the rich-argument serializer.

## Understand response ownership

Core owns the transport:

- It identifies scripted and unscripted calls.
- It decodes URL and form arguments.
- It provides the default `createNoJSHandler()` response for browser form posts.
- It redirects a POST with status 303 and stores a non-`Response` outcome in a one-shot flash cookie.
- It exposes `handleNoJS` so an integration can replace or extend that response policy.
- It preserves response status, headers, bodies, redirects, and revalidation metadata.

The router owns submission behavior:

- It reads and clears the flash cookie during the next server render.
- It turns the decoded outcome into router submission state.
- It connects revalidation metadata to the query cache.

The core default works when a custom host dispatches the request through `handleServerFunctionRequest()`.
A custom host can configure `createNoJSHandler()` with a base path or provide another `handleNoJS` implementation.

Keep application validation and authorization inside the server function.
No-JavaScript requests reach the same implementation as scripted requests.
