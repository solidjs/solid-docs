Routing is an application integration rather than a requirement of Solid.
A router integration owns URL matching, navigation, and route rendering.
Route-level data can use the router's data APIs or a separate cache.
The application renders the router as part of the component tree.

The `bare` project shape has no router.
The `basic` and `fullstack` shapes use Solid Router, and `fullstack-tanstack` uses TanStack Router.
This page explains what a router needs from the platform and how the two supported routers plug in.
The router-specific guides are [Solid Router](/routing/solid-router) and [TanStack Router](/routing/tanstack).

## Pick a router

Use Solid Router when you do not have a reason to use something else.
It is built for Solid's reactivity model: route params and location are reactive values, `query()` and `action()` are thin wrappers around server functions, forms submit before JavaScript loads, and single-flight mutations work by default.
It also ships the file-system adapter that the CLI templates use, so routes are files under `src/routes`.

Use TanStack Router when you already build on TanStack Query, need its typed search-parameter schemas and loader model, or share routing conventions with a TanStack app in another framework.
You give up the file-system convention shared with the rest of the Solid templates, and you own the data cache handoff between server and client, which the [TanStack Router](/routing/tanstack) page documents.

Both routers are mounted the same way and both use the same server-side hooks, so the rest of this page applies to either one.

## The smallest routed app

This is the `basic` template with the comments removed.
The router is created once at module scope:

```ts
// src/router.ts
import { pageRoutes } from "virtual:file-routes";
import { createRouter } from "@solidjs/router";
import { fileRoutes } from "@solidjs/router/fs";

export const Router = createRouter({ routes: fileRoutes(pageRoutes) });

export const { paths } = Router;
```

And mounted in `App`, where the matched page renders through `props.children`:

```tsx
// src/App.tsx
import { Loading } from "solid-js";
import { paths, Router } from "./router";

export default function App() {
	return (
		<Router>
			{(props) => (
				<>
					<nav>
						<a href={paths()}>Home</a>
						<a href={paths.users(1)}>Users</a>
					</nav>
					<Loading fallback={<main>Loading…</main>}>{props.children}</Loading>
				</>
			)}
		</Router>
	);
}
```

Each file under `src/routes` with a default export is a page.
`paths` builds URLs from the route tree, so links are checked by the type checker.
The `Loading` boundary around `props.children` is what lets a navigation keep the current page on screen while the next page's data loads.
The [Solid Router setup page](/routing/solid-router/setup) shows the same app with an in-memory route tree instead of the file-system adapter.

## Mount the router in `App`

The `@solidjs/vite-plugin` start mode uses `src/App.tsx` as the root component for its generated entries.
With server-side rendering (SSR) enabled, its generated server and client entries both render `App` inside `src/Document.tsx`.
Mount the router or its provider in `App` so both entries use the same router root.
Site-wide providers can wrap the router, and shared layouts can live in the router's root route or inside its provider.

## Choose how routes are defined

The platform does not prescribe route definitions or file naming.
A router can consume an in-memory route tree, its own generated route tree, or a manifest from a file-system routing plugin.

The `filesystem-routing` Vite plugin exposes its manifest through `virtual:file-routes`.
Solid Router can convert the manifest's `pageRoutes` export into route definitions with `fileRoutes` from `@solidjs/router/fs`.
This import and adapter are Solid Router conventions, not requirements for other routers.

TanStack Router uses `@tanstack/router-plugin` to generate its own typed route tree from `src/routes`.
An application can still use `virtual:file-routes` for HTTP handlers in another directory, as the Router + Query template does for `src/api`.

## Connect routing to requests

During SSR, a router needs the request URL and any request-scoped data required by its loaders.
The start mode request handler creates a `RequestEvent` for each web `Request` and runs the render inside that event's scope.

Solid Router reads the request URL from that event when it creates its server integration.
That behavior belongs to Solid Router.

Routers that need an asynchronous preparation step can use the platform's `start.setup` option.
The configured server-only module runs when the middleware chain reaches the page render and before `renderToStream`.
It can create request-local router and cache instances, load the matched routes, and return a component to render in place of `App`.
The hook runs once each time a generated server entry renders an SSR request and is ignored when SSR is disabled.
An authored server entry already owns the render function and must perform the same preparation itself.

The separate `start.middleware` option installs fetch-style middleware in front of page renders, server-function calls, and other requests dispatched by the handler.
The middleware chain and `start.setup` share the same request event, including values stored in `event.locals`.

## Integrate single-flight mutations

Single-flight combines a mutation result and refreshed page data in one server-function response.
The platform transport supplies two router-neutral extension points:

- Registering a client consumer with `subscribeFlightData` adds the single-flight request header to non-GET server-function calls.
- A server `collectFlightData` hook receives the target URL, revalidation keys, and request headers with mutation cookies already folded in.

The server-function runtime awaits the consumer before resolving the call with the mutation value.
The integration decides how to match the target URL, rerun relevant loaders or preloads, produce a serializable payload, and apply it on the client.
`serverFunctions.configure` provides a server-only module that the generated handler imports before dispatch in development and production.

Solid Router supplies `createFlightDataCollector` from `@solidjs/router/server`.
It consumes the router's route tree, base, and root preload, then collects matched `query` results for the target URL.
On the client, Solid Router enables single-flight by default, registers the mounted router, and installs its flight consumer when the first router action is created.
The router and action integrations use a rendezvous so either can load first.
The consumer applies response metadata and seeds Solid Router's `query` cache from the payload.

Other routers provide their own collection and cache-hydration policy.
The [TanStack Router integration](/routing/tanstack) uses a dehydrated TanStack Query cache as the flight payload.
