## Why it fires

A response header was written after the head was sent; the write was dropped (dev throws instead).
`data.method`/`data.name` say which.

:::note[Server rendering]
The server runtime reports on the same channel, with the same `in <App> › <Page>` line.
Two groups.
**Findings** ([`SSR_RENDER_ERROR_CONTAINED`](/reference/solid-js/diagnostics/ssr-render-error-contained), [`SSR_SUBTREE_ABANDONED`](/reference/solid-js/diagnostics/ssr-subtree-abandoned), [`SSR_STREAM_ABANDONED`](/reference/solid-js/diagnostics/ssr-stream-abandoned), `LATE_HEADER_WRITE`, [`DYNAMIC_ASYNC_COMPONENT`](/reference/solid-js/diagnostics/dynamic-async-component), [`ASYNC_MEMO_ELEMENT`](/reference/solid-js/diagnostics/async-memo-element), [`SERVER_ERROR_SANITIZED`](/reference/solid-js/diagnostics/server-error-sanitized), [`FRAME_MARKER_CORRUPTED`](/reference/solid-js/diagnostics/frame-marker-corrupted)) are facts about a render that exist in observe builds too — an APM sees them in production; in dev they print.
**Checks** (the rest, [`SSR_BOUNDARY_WATERFALL`](/reference/solid-js/diagnostics/ssr-boundary-waterfall) and [`SSR_CLIENT_CONTENT_MASKED`](/reference/solid-js/diagnostics/ssr-client-content-masked) included) are dev-only guidance.
A captured artifact from a server render carries both.
:::

## How to fix it

Move the write before the first flush — before any `<Loading>` fallback can ship — or before the handler returns; a cookie set from inside a late-streaming component never reaches the browser.
