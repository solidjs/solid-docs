Effect's write provably feeds back into its own inputs; `info` for multi-effect rings (attribution enabled).

## What you saw

- **Kind:** `perf`
- **Severity:** `info` (advisory, delivered on the diagnostics channel and never printed) or `warn` (code that works but is structurally wrong or expensive)

In a captured artifact the same finding is an event with `code: "EFFECT_WRITES_OWN_SOURCE"`, `ownerPath`, and `loc`.

## Why it fires

An effect re-ran because of a write it made itself: its callback wrote a value that its own inputs depend on (directly, or through the memos the message names), so the flush settled in two passes and the screen rendered the pre-write value in between.
The effect converged — an infinite loop throws on its own — which is exactly why nothing else reports it.
Typical shapes: clamping (`if (page() > max()) setPage(max())`), resetting one signal when another changes, filling a default, normalizing input.

:::note[Performance pathologies (from the attribution engine)]
These fire only while attribution is enabled and describe cost, not incorrect behavior.
The numbers in the message are measurements, not guesses.
:::

## How to fix it

The written value is a function of what the effect reads, so it is a memo: `const page = createMemo(() => Math.min(rawPage(), max()))`, or normalize where the source is _written_ (in the setter/handler) instead of correcting it afterwards.
The `info` form names a cycle relayed across several effects (`A` writes `x`, `B` reads `x` and writes `y`, `A` reads `y`) — same repair: derive every relayed value from the original inputs and drop the writes.
The walk follows graph edges only; a write fed back through untracked indirection is not claimed.
