## Why it fires

A stateful property binding (`value`/`checked` on an input, `value` on a textarea, `selected` on an option, `muted` on media) re-wrote the value it wrote last time over an edit the user made and never committed to the bound signal — the typed text (or toggled box) is lost.
The binding shares its template's grouped effect, so any other dynamic attribute in the same template changing re-runs it; so does a spread re-run or an `equals: false` source firing an equal value.
Typical cause: `value={props.name} onChange={commit}` with no draft signal.
Once per element and property; the write still happens.

**Findings** ([`SSR_RENDER_ERROR_CONTAINED`](/reference/solid-js/diagnostics/ssr-render-error-contained), [`SSR_SUBTREE_ABANDONED`](/reference/solid-js/diagnostics/ssr-subtree-abandoned), [`SSR_STREAM_ABANDONED`](/reference/solid-js/diagnostics/ssr-stream-abandoned), [`LATE_HEADER_WRITE`](/reference/solid-js/diagnostics/late-header-write), [`DYNAMIC_ASYNC_COMPONENT`](/reference/solid-js/diagnostics/dynamic-async-component), [`ASYNC_MEMO_ELEMENT`](/reference/solid-js/diagnostics/async-memo-element), [`SERVER_ERROR_SANITIZED`](/reference/solid-js/diagnostics/server-error-sanitized), [`FRAME_MARKER_CORRUPTED`](/reference/solid-js/diagnostics/frame-marker-corrupted)) are facts about a render that exist in observe builds too — an APM sees them in production; in dev they print.

A captured artifact from a server render carries both.

## How to fix it

Fix: write the signal on every edit (`onInput={e => setDraft(e.currentTarget.value)}`, commit the draft separately), use `defaultValue`/`defaultChecked` for an uncontrolled element, or reject an edit by writing the accepted value back in the handler (`e.currentTarget.value = next`) instead of re-asserting an equal value through the signal.
